# Ручной смоук-тест для Лин (мини-ПК)

Всё, что физически нельзя проверить в песочнице (нет сети, нет реального Telegram-аккаунта, нет X-сервера, нет самого файла rubedo4). Три пункта из этапа 9.6 — ядро списка; остальное — накопленные по ходу реворка гэпы, собранные сюда в одно место, чтобы не были разбросаны по коммитам.

Порядок важен: пройти сверху вниз — каждый следующий пункт предполагает, что предыдущие уже прошли.

## 1. Первый запуск: `.env` + база

- [ ] Скопировать `.env.example` → `.env`, заполнить: `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `OWNER_USER_ID`, ключи LLM (`OPENROUTER_API_KEYS`, `GROQ_API_KEYS`), `DATABASE_URL`.
- [ ] Postgres 16 с `pgvector`/`pg_trgm`, затем один раз: `python -c "from memory.db import init_db; init_db()"`.
- [ ] `pip install -r requirements.txt` (если `telethon` не ставится из-за старого `pyaes` против нового `setuptools` — тот же фикс, что и в CI: `SETUPTOOLS_USE_DISTUTILS=stdlib pip install -r requirements.txt`).

## 2. Telethon-логин (этап 9.6 — только руками)

`TelethonTransport` ни разу не запускался вживую — нет сети/аккаунта в песочнице.

- [ ] `python -m interface.telegram` (или через `launcher.py`) — первый запуск попросит номер телефона и код подтверждения, это интерактивно и может сделать только Лин.
- [ ] После логина — сессия сохраняется (`rubedo.session` рядом с процессом), повторных логинов при обычных рестартах быть не должно.
- [ ] Отправить простое сообщение («привет») — убедиться, что ответ приходит.

## 3. Reply-тест (этап 9.6 — только руками)

Детерминированная жёсткая привязка ответа к сессии (`agent/routing.py`, `message_bindings`) протестирована полностью на `LocalTransport`, но реальный `event.reply_to.reply_to_msg_id` от Telethon — нет.

- [ ] Спровоцировать `ask_user` (например: «разбери почту» — должно потребовать уточнения) — придёт вопрос.
- [ ] Ответить на это сообщение через **Reply** в Telegram (не просто новым сообщением) — убедиться, что ответ ушёл именно в ту сессию, а не потребовал уточнения «это про что?».
- [ ] Параллельно спровоцировать второй висящий вопрос (например, жёлтое подтверждение) и повторить reply на первый — оба должны разрешиться правильно, без обращения к LLM-классификатору для разруливания (можно проверить по логам — не должно быть лишнего вызова классификатора на этот конкретный ответ).

## 4. kill -9 тест (этап 9.6 — только руками)

Восстановление после сбоя (`agent/crash_recovery.py`) читает только состояние в Postgres, так что «убила ли её kill -9 или что-то ещё» для логики не важно — но реальный процесс-супервизор (`launcher.py`) и реальный Telegram-канал доставки «продолжить?» проверены только по отдельности (супервизор — на тестовых процессах, восстановление — на `LocalTransport`), не вместе, вживую.

- [ ] Начать что-нибудь многошаговое («настрой автобэкап» и подобное, чтобы появилась активная сессия).
- [ ] Пока сессия активна — `kill -9 <pid процесса interface.telegram>` (не `launcher.py` — его отдельно можно тоже, но именно child).
- [ ] `launcher.py` должен обнаружить смерть процесса и перезапустить его (смотреть `logs/rubedo.log`).
- [ ] После перезапуска — в Telegram должно прийти сообщение «...Продолжить?» с кратким описанием прерванной задачи.
- [ ] Ответить «да» — убедиться, что она резюмирует по-настоящему (свежее рассуждение с контекстом сбоя), а не слепо повторяет прерванный шаг.

## 5. Дисплей — экран и будильник (этап 8-9.5, только руками)

Pygame-рендеринг не проверяется в песочнице вообще (нет X-сервера) — только логика (`_compute_session_state`, `set_background`, чтение флагов из Postgres).

- [ ] `ENABLE_DISPLAY=1` в `.env`, перезапуск — окно должно появиться на экране мини-ПК.
- [ ] Проверить приоритет состояний: во время работы — «thinking», во время висящего вопроса — «waiting» (должно перебивать «thinking», если параллельно работает вторая сессия), в простое — «idle».
- [ ] `set_background(path)` (попросить её сменить фон на что-то из `workspace/backgrounds/`) — убедиться, что применяется без рестарта дисплея.
- [ ] Будильник: дождаться (или спровоцировать) срабатывание — физический экран должен показать экран будильника, тап 3 раза — должен выключиться, и день должен реально перейти из ночи в утро (не только визуально погаснуть экран).

## 6. Секреты — `git filter-repo` по rubedo4 (этап 9.1, требует твоего «go» в моменте)

Дочистка `.env` из истории rubedo4 подготовлена и провалидирована локально (dry-run на зеркале репозитория), но **не выполнена** — переписывание истории с `force-push` не делается без явного разрешения в моменте.

- [ ] **Сначала** — ротация ключей (Telegram API, OpenRouter, Groq, Tavily) и смена sudo-пароля. Без этого чистка истории бессмысленна: те же ключи, скомпрометированные или нет, продолжат работать.
- [ ] После ротации — дать явное «go» на выполнение `git filter-repo --path .env --invert-paths --force` + `git push --force --all/--tags` по rubedo4.
- [ ] После force-push — предупреждение: любые существующие локальные клоны rubedo4 придётся переклонировать (старые ссылаются на переписанную историю).

## 7. Перенос памяти (готов, не выполнен)

`scripts/migrate_from_rubedo4.py` проверен на синтетической копии схемы — не на настоящем `data/rubedo.db`.

- [ ] `python scripts/migrate_from_rubedo4.py /path/to/rubedo4/data/rubedo.db` (без `--apply`) — свериться со счётом, что выглядит разумно.
- [ ] `python scripts/migrate_from_rubedo4.py /path/to/rubedo4/data/rubedo.db --apply` — реальный перенос.
- [ ] Проверить, что `messages` (последние 20) действительно с тегом `[закрыто]` у пользовательских строк.
