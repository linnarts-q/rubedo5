## 0. Цель одной фразой

Агент, который в простое сам находит себе осмысленную работу, доводит задачи до конца через анализ собственных ошибок, спрашивает когда данных не хватает, и при этом физически не способен молча сломать прод или самого себя.

Четыре оси: инициатива, компетентность, вопросы, доверие. Плюс сквозная инфраструктура — сессии задач.

## 1. Модель доверия — три зоны

Заменяет плоскую модель (9.5). Зона определяется **детерминированно** — по хосту, пути и типу операции, а не по угадыванию «опасности» команды regex-ом. Denylist (9.3) остаётся как последний рубеж, но перестаёт быть единственной защитой.

### 🟢 Зелёная — делает сама, без спроса
Личный workspace + дополнительные (её собственные) инструменты + мини-ПК в пределах её процессов.

- Файловые операции внутри `workspace/` (4.1)
- Веб: поиск, чтение, скриншоты, research (4.4)
- Задачи, напоминания, недельные события, pool, rubedo_queue (4.5–4.10)
- Диагностика, чтение своих логов (4.13)
- Отправка файлов/фото пользователю (4.14)
- `run_code` — в песочнице, ограниченной workspace
- Чтение чего угодно в любой зоне («изучать можно всё» — С2, С4, С12)
- Собственные инструменты в workspace: создание, правка, починка (см. §8)

### 🟡 Жёлтая — сначала спрашивает, потом делает
Основные инструменты + сервер (пользовательский уровень).

- SpotRent-контроль: start/stop (4.12); `status` — зелёный
- Shell-команды на сервере без sudo
- Установка пакетов (pip/npm) вне её собственной песочницы
- Запись файлов за пределами workspace
- Рестарт сервисов, затрагивающих живых пользователей (С13)

Механика: инструмент возвращает не результат, а «запрос на подтверждение» → сообщение Лин с описанием действия и последствий → выполнение только после явного «да». Запрос живёт как «висящий вопрос» (§5).

### 🔴 Красная — только по прямому указанию, сама только читает
Ядро Рубедо, система мини-ПК, система сервера.

- `run_sudo`, `system_update` (4.2, 4.11)
- `set_env_var` (4.15); команду `/env` (1.6) — удалить полностью, риск описан в 9.4
- `self_update`, `agent_restart` (4.11) — по флоу из §8
- Изменение кода ядра, systemd-юнитов, cron вне её песочницы
- Kill чужих процессов (4.3)

«По прямому указанию» = Лин явно попросил это конкретное действие в этом диалоге. Инициативное предложение красного действия допустимо, выполнение — нет (С13).

## 2. Сессии задач ← новое ядро исполнения

Метафора: задача = открытое окно терминала. Все шаги задачи живут в нём; новая задача = новое окно; пауза = свернуть, не закрыть.

**Что такое сессия:**
- Собственная история шагов (tool-вызовы, результаты, промежуточные выводы) — не смешивается с другими задачами и с болтовнёй
- Собственное рабочее состояние: cwd, временные файлы, при необходимости — живой shell-процесс (tmux-сессия на задачу — буквальная реализация метафоры) и браузерный контекст для веб-сёрфинга: один headless-браузер на агента, **вкладка/контекст на сессию** (не браузер-на-сессию — Chromium ест 300–500 МБ, на 4 ГБ это непозволительно)
- Статус: `running / paused / waiting_user / waiting_dependency / done / failed`
- Сериализация в SQLite при паузе — переживает рестарт агента

**Что это чинит:**
- Обрезка контекста до 6 сообщений (2.4) убивала середину длинной задачи → теперь каждая сессия помнит только своё, бюджет контекста расходуется на дело
- С15: «поставь на паузу, глянь срочное, вернись» — становится штатной операцией
- «Висящий вопрос» (§5) = сессия в `waiting_user`, а не протухающий intercept

**Маршрутизация сообщений (нерешённое, обсудить):**
Когда активны 2+ сессии, входящее «да, продолжай» неоднозначно. Варианты: (а) дешёвый Groq-проход определяет адресата по содержанию; (б) последняя сессия, задавшая вопрос, — дефолтный адресат; (в) reply на конкретное сообщение Рубедо жёстко привязывает к сессии (1.5 уже отдаёт reply-контекст). Предлагаю (в) как жёсткое правило + (б) как дефолт + (а) как разрешение конфликтов.

**Этапность:** фаза 1 — сессии с паузой, выполнение последовательное (одна running, остальные paused/waiting). Фаза 2 — параллельность: 2–3 одновременных сессии, семафор на LLM-вызовы (rate limits OpenRouter/Groq), блокировки на запись в общую память. Не начинать фазу 2, пока фаза 1 не отстоялась.

## 3. Рефлексивный цикл (С5, С6, С7)

Расширение executor (2.4). Сейчас: ошибка → тупой ретрай или стоп. Станет:

```
ошибка/тупик
  → анализ через Groq (6.2): что пошло не так?
  → выбор ветки:
      a) поправить аргументы/код → ретрай
      b) другой инструмент или подход
      c) research: web_search/документация «как правильно делать X» (4.4)
      d) вопрос Лин (→ сессия в waiting_user)
  → лимит рефлексий на задачу (например 3), дальше — честный отчёт о неудаче
```

Плюс **планирование перед незнакомой задачей** (С6): если в `experience` нет похожего опыта — сначала план + проверка окружения + изолированный тест, потом внедрение.

Результат каждого цикла пишется в `experience` (§7).

## 4. Пост-верификация (С8, С6)

Отдельный шаг после «выполнено»: перечитать результат, сверить с намерением. Нашла ошибку после отчёта → сообщает сама («перепроверила, три файла кривые, исправить?»), не молчит. Для изменений в жёлтой/красной зоне верификация обязательна *до* отчёта.

## 5. Висящие вопросы (С9, С10, С11)

Сущность `pending_question`: сессия, текст вопроса, время. Эскалация: спросила → нет ответа → одно напоминание → нет ответа → задача-напоминание на завтра. Заменяет TTL-intercepts из meta (2.2, 3.7). Уточнение посреди выполнения (С10) — это просто сессия, ушедшая в `waiting_user` и продолжившая после ответа: механизм тот же.

## 6. Idle-агенда (С1, С4)

Когда нет running-сессий и очередь пуста (редкое событие — раз в 1–2 недели):
1. Паттерн-майнинг памяти: неявные регулярности («что бывает по вторникам»)
2. Health-sweep всей системы, не только нагрузки компонентов: CPU/RAM/диск, интернет-связность, заряд/питание, доступность сервера, отклонения от нормы; критические пороги → `critical` из §7. Опционально — визуальный отчёт: метрики из Netdata API (`/api/v1/data`) → matplotlib → картинка через 4.14 (предложение самой rubedo4, кандидат на её первый самописный инструмент)
3. Research по открытым планам Лин или собственным wishes (3.6) — результат в отчёт
4. Самооптимизация — только в зелёной зоне; идеи по ядру → PR-флоу (§8)
5. Если совсем ничего — один вопрос «есть задачи?» с cooldown (константа, например 24ч)

## 7. Уровни уведомлений (С3, С16)

Три уровня вместо бинарного подавления (5.8):
- `critical` — пробивает всё: day-off, тихие часы, паузы (перегрев 88°C, упавший SpotRent)
- `important` — пробивает day-off, уважает ночные тихие часы; может прервать текущую тему разговора (страховка, С3)
- `routine` — уважает все тихие режимы, бандлится (nudges, отчёты idle-агенды)

Уровень назначает источник события + Groq-проход для спорных.

## 8. Самоулучшение: PR-флоу (красная зона, ядро)

Дефолт «ядро красное, но предлагать ≠ применять»:
- Читать свой код, анализировать, писать диффы, коммитить в свою ветку — свободно (это «изучение»)
- Merge в main + рестарт — только Лин
- `self_update` (4.11) остаётся, источник — ветка после аппрува
- Её *собственные* инструменты в workspace — зелёная зона: пишет и чинит сама (это делает С5 «исправит код и перезапустится» легальным, если конвертер — её скрипт, а не ядро)
- Пометка: пересмотреть (автомерж мелочей) после ~10 успешных PR

Рестарт агента откладывается, если есть активная сессия по задаче от Лин.

## 9. Оживление `experience` (3.8, С8)

Таблица перестаёт быть мёртвой: запись после каждого рефлексивного цикла и каждой пост-верификации — задача, подход, результат, вывод. Читается: перед незнакомой задачей (§3) и в самоотчётах. `working_memory` — удалить из схемы, её роль забирают сессии (§2).

## 10. Гигиена перед стартом (9.4) — до любого кода

- Новые секреты: Telegram API, OpenRouter, Groq, Tavily, пароль sudo
- `.env` — вон из git-истории (filter-repo), в `.gitignore`

## 11. Гибкая память

Проблема: вся память льётся в каждый промпт как есть → слабая модель повторяет уже закрытые поручения («выполни А» из истории побеждает текущее «выполни Б» или «спасибо»). Четыре слоя, от дешёвого к дорогому:

1. **Аннотация исходов.** При сборке промпта каждое прошлое поручение помечается статусом: `[выполнено]` / `[провалено, отчитано]` / `[отменено]`. Закрытый эпизод перестаёт читаться как приказ. Требует: связка «поручение → исход» в истории сообщений (3.1).
2. **Директива ≠ справка.** Жёсткая структура промпта: блок «прошлое — только контекст, НЕ выполнять» отдельно от «текущий запрос — единственное действие». Явное фехтование, критично для free-tier моделей.
3. **Tools-gate по роуту.** На роутах `chat`/`emotional` (2.1) executor не получает TOOLS_MAP вообще — «молодец, спасибо» физически не может дёрнуть инструмент. Детерминированно, нулевая цена.
4. **Ретривал вместо тотальной инжекции.** Факты/эпизоды подтягиваются FTS-поиском (3.3) по релевантности текущему запросу, а не все подряд в пределах бюджета (6.4). Отладка парсера и болтовня про ужин требуют разной памяти.

Слои 1–3 не трогают схему БД — можно катить как хотфикс в rubedo4 до основного реворка. Слой 4 — после сессий (§2), т.к. запрос-контекст сессии и есть ключ ретривала. Сессии дополнительно изолируют задачи друг от друга (задача Б не видит команду А).

**Перенос данных из rubedo4** (одноразовый, перед первым запуском rubedo5 «в бою»): `scripts/migrate_from_rubedo4.py <путь к data/rubedo.db>` — таблицы схемы почти 1:1 с Postgres-версией (см. выше), перенос механический. Полностью переносится курированная память (facts, summaries, events, experience, internal_notes, wishes, day_tasks, recurring_tasks, week_events, rubedo_tasks, insights, pool_tasks, rubedo_queue(+recurring), profiles); `messages` — только последний срез (`--messages-limit`, по умолчанию 20 строк), не вся сырая история (решение Лин). `working_memory`/`day_state`/`day_phase_state` и новые в rubedo5 сущности (`task_sessions` и всё вокруг сессий, `agent_state` и т.п.) не переносятся — либо мертвы, либо не существовали в rubedo4. Без `--apply` скрипт только считает и печатает план, ничего не пишет; идемпотентен (сохраняет исходные id, `ON CONFLICT DO NOTHING` — повторный запуск безопасен).

## 12. LLM-слой: дисциплина вызовов (6.x)

- **Два tier-списка вместо одной цепочки:** `fast` (классификация, severity, маршрутизация сообщений) и `smart` (рефлексия, планирование, idle-агенда). Внутри каждого — своя цепочка фолбэков; не жёсткая привязка «роль → модель», а «роль → tier», чтобы переживать лимиты Groq. Конкретный состав моделей — как сейчас, пересмотр отложен (решение Лин).
- **Схема-валидация структурированных ответов:** каждый tool-вызов и JSON-ответ проверяется по схеме. Невалидно → ровно **один** repair-проход («вот ответ, вот ошибка парсинга, почини») → невалидно снова → в рефлексивный цикл (§3) как обычная ошибка. Гипотеза: заметная доля «тупости» — это криво распарсенный вывод, а не глупость модели.

## 13. Реестр инструментов

~90 инструментов (4.x) в каждом промпте — перерасход бюджета (6.4) и каша для слабой модели. Вместо этого:

- Инструменты группируются в категории (файлы, веб, задачи, сервер, самоанализ, ...), каждая с зоной из §1
- **Классификатор (2.1) выбирает категории заранее** — новое поле `tool_categories` в его выводе (решение Лин)
- Базовый набор присутствует всегда: `ask_user`, `report`, `plan` — они нужны любой задаче
- Страховка от мисклассификации: если в рефлексивном цикле (§3, ветка b) модель приходит к «нужен инструмент, которого нет в промпте» — один дозапрос категории на задачу, дальше честный отказ. Это не гибридный режим, а аварийный клапан.

## 14. Журнал решений

Таблица `decisions` (Postgres): `session_id`, время, действие, зона, «почему» одной фразой из вывода рефлексии/idle-агенды, ссылка на запись `experience` если есть. Пишется при **каждом инициативном** действии (не по прямой команде). Ретеншн — не чистим, объёмы копеечные.

Доступ (решение Лин): Лин — через БД/логи; Рубедо — читает свой журнал как источник самоанализа (зелёная зона, категория «самоанализ» из §13). Команда `/why` в Telegram — не делаем.

## 15. Обратимость и прозрачность автономии

Тема: не «что она может», а «как Лин живёт рядом с этим».

- **Стоп-фраза.** Заранее оговорённая фраза, проверяемая **детерминированно** (сравнение строки на входе, 1.5, до любого LLM) — работает, даже когда модели легли или тупят. Эффект: все сессии → paused, автономка замирает, реагирует только на прямые команды до явной «отморозки».
- **Undo для жёлтой зоны.** Перед любой записью в жёлтой зоне — автоснапшот затрагиваемых файлов в `workspace/undo/` (TTL ~2 дня) + инструмент `rollback_last`. Цель: сделать аппрувы психологически дешёвыми — «откачу если что».
- **Dry-run в запросе подтверждения.** Где инструмент позволяет — к запросу «можно?» прикладывается факт, а не сгенерированное описание: для `rm` — реальный список удаляемых файлов, для systemd — статус юнита до. Реализовывать по инструментам постепенно, начиная с самых опасных.
- **Вечерний дайджест.** Одно `routine`-сообщение в конце дня поверх журнала (§14): что сделала сама, что висит в вопросах (§5), что в очереди. Три строки, бандлится по правилам §7.

## 16. Режимы работы

Режим = пресет из трёх вещей: промпт личности/поведения + набор категорий инструментов (§13) + правила уведомлений (§7). Первые два пресета:

- **Ассистентский** (утро/вечер, day-engine): будильник, брифинг, врапап; тон и промпт под бытовое; рабочие категории инструментов не грузятся
- **Рабочий** (активные сессии с задачами): промпт под исполнение, полный релевантный набор категорий, лаконичность

Динамика будильника: жёсткой авто-побудки **нет** — цена ошибки слишком высока. Вместо этого вечером она *предлагает* время подъёма (по календарю/планам завтрашнего дня), Лин подтверждает или правит одним ответом — механика висящего вопроса (§5) с дефолтом «вчерашнее время», если не ответил. Аналогично время брифинга/врапапа — динамичное, привязано к фактическому подъёму/завершению дня, не к константам `_CADENCE`.

Переключение режимов — day-engine по расписанию + вручную командой. Отложено до локальной LLM (вне спеки): самостоятельное создание суб-агентов.

## 19. Дисплей: консервативный порт + фон

Принцип: не переделывать — pygame-слой и аватар (rubedo4 `display/window.py`) переносятся как есть, полный редизайн будет отдельно и позже (решение Лин). Ровно два изменения:

1. **Адаптация `DisplayState` к сессиям.** Вместо одной активности — приоритет: error > waiting_user > working > idle. Есть сессия в `waiting_user` → показываем ожидание, даже если вторая параллельно работает (§2, фаза 2 — сессии теперь реально могут сосуществовать). Маппинг тривиальный, читается из статусов `task_sessions` в БД, не из шины. `error` остаётся переходной вспышкой от шины (`AgentError`), т.к. голого опроса недостаточно чтобы отличить «упало только что» от «упало вчера».
2. **Фон — новый инструмент зелёной зоны `set_background(path)`.** Только файлы из `workspace/backgrounds/`, проверка формата и разрешения перед применением, выбор персистится в БД (переживает рестарт, переживает пересоздание процесса дисплея). Источники фонов — её же зелёные возможности (скачать из веба, сгенерить matplotlib/PIL) — без отдельных механизмов. Смена по её инициативе = инициативное действие → запись в журнал решений (§14, уже покрыто общей конвенцией — специальной обработки внутри инструмента не нужно). Опционально — одной строкой в idle-агенде (§6, когда та появится): «иногда обновить фон под настроение/сезон», без расписания, по желанию.

Необходимая (не одна из «двух изменений») попутная адаптация: `_load_plan`/`_load_queue` переведены с `sqlite3` на `memory.db.get_conn()` — SQLite в rubedo5 не существует с этапа 1.5, копия с прежним драйвером была бы нерабочей, а не консервативной.

Известный, сознательно не тронутый разрыв: экран будильника (тап-для-отключения) в rubedo4 читает файлы-флаги (`_ALARM_ACTIVE_FILE`/`_ALARM_DISMISSED_FILE`); day-engine 5.0 будит через Postgres `meta` + `notify.deliver()` и эти файлы никогда не пишет — физический экран будильника сейчас не может активироваться. Перепроводка — третье изменение сверх заявленных двух, оставлена как отдельный будущий шаг.
